# 软件通用工程｜AI 研发交付与质量验收

把软件需求推进到“结果可观察、证据可复核、边界可追责”的完成状态。这个技能不是一套框架模板，而是一种在真实仓库中保护已有资产、补齐最小业务闭环、逐层收敛风险的工程方法。

## 何时启用

当任务涉及多步骤开发、跨端联动、接口或权限变更、半成品收敛、真实环境验收、上线判断或交付报告时启用。简单语法问答、翻译、单句润色和不涉及工程边界的小编辑无需启用。

## 1. 建立基线与任务契约

先区分本轮是解释、诊断、审查、设计、修改还是发布；授权决定能走到哪一级，不把“帮我看看”扩展成推送或上线。

阅读仓库说明、适用的 `AGENTS.md`、近期相关提交和实际运行入口。对 Git 仓库核实：

```text
git status --short --branch
git rev-parse HEAD
git worktree list
git diff --stat
git diff --cached --stat
```

记录必须保留的用户改动、未跟踪成果、受保护契约和本轮允许变更的文件。区分代码事实、当前执行证据与历史记录；旧报告不替代当前候选验证。

把需求写成可验收的任务契约：

- 入口、角色、动作和成功后的可观察结果。
- 输入、输出、错误、权限、状态变化和兼容约束。
- 本轮包含与不包含的范围，以及每项对应的证据。

## 2. 沿真实调用路径核对契约

从入口阅读到客户端适配、服务端处理、数据访问和外部依赖。接口“存在”不等于契约匹配，重点核对字段语义、分页总数、完整标识符、空值、金额单位、错误与权限来源。

按实际风险守住以下不变量：

| 领域 | 工程不变量 |
| --- | --- |
| 分层与数据归属 | 沿用项目既有分层；业务判断和权限放在规定位置，不为演示另建旁路。 |
| 状态推进 | 保留合法转换与终态；已有版本号或 CAS 时拒绝过期写入。 |
| 重试与副作用 | 区分同一意图重试与新意图；沿用既有幂等、Outbox/Inbox 或等价机制。 |
| 权限与可见性 | 未知或失败的鉴权、审核、归属判断不能被当作放行；UI 隐藏不代替服务端保护。 |
| 金额与配置 | 沿用整数分或项目既定精确类型；历史交易按发生时快照解释，不按新费率重算。 |
| 数据迁移 | 对照当前迁移登记与真实 schema；不硬编码历史“下一号”，记录兼容与回退策略。 |

这些是按风险选择的检查，不要求每个项目引入额外架构。只在业务需要且已授权时增加机制。

## 3. 以最小闭环实施

优先复用现有组件、服务、错误类型和测试入口。先修正契约，再连通真实读写，最后处理交互与视觉；跨端变更逐一记录每端是否落地。

视觉或交互改动仍须保留真实数据、分页、导航参数、身份切换和功能开关，并检查空态、加载失败、长文本、大数值、窄屏、滚动、键盘遮挡和返回路径。新增控件必须产生真实结果，或明确呈现不可用状态。

修复缺陷优先复现真实失败路径；按风险补充能证明行为的回归测试。不要用“按钮存在”或源代码字符串匹配代替运行证据。

遇到环境故障先查依赖、版本、磁盘、端口和进程，不把资源问题误判成产品问题，也不自动清理或终止不属于本任务的资源。

## 4. 用证据分层验收

需要详细检查时读取 [验收清单](acceptance-checklist.md)。根据风险从相关检查逐步扩大，并确认测试是否会写库、上传、发消息或触发计费。

每项结果写明目标、环境、执行方式和状态：`PASS`、`FAIL`、`BLOCKED`、`NOT_RUN` 或有理由的 `N/A`。至少区分：

1. 静态与自动化：类型、边界、测试、构建。
2. 本地运行：真实操作、错误路径和刷新后的持久化结果。
3. 指定集成环境：真实数据库与外部服务。
4. 设备与平台：真机、多账号、权限、审核和平台状态。
5. 发布后：候选版本已部署、关键路径回归和回滚保障。

隔离库、mock、健康接口或旧截图只能证明各自范围，不能替代指定环境、双端设备或当前提交的证据。缺少证据的层级保留未验证状态。

## 5. 交付与发布收口

读取 [报告模板](report-template.md)，按任务规模输出结果。交付时说明做了什么、依据什么认定有效、还有什么阻断，以及临时文件、测试数据、服务和云对象的归属。

当用户已授权提交或发布时：

- 只暂存本任务文件，复核 staged diff，再使用中文提交信息。
- 推送前核对目标仓库、分支和提交范围；使用普通推送，不强推或重写共享历史。
- 推送后核实远端提交。代码推送、平台上传、审核通过、发布生效和真机验收分别报告，不互相推导。

发布到生产、提交审核、改变权限或向第三方发送消息，必须有对应授权；准备好本地候选包不等于已上架或已产生收入。

## 6. 统一状态语言

用精确状态代替笼统的“完成”：

- `PASS`：在指定提交、环境和条件下实际满足验收标准。
- `FAIL`：已执行但结果不满足标准。
- `BLOCKED`：缺少环境、权限、数据或外部状态，无法完成。
- `NOT_RUN`：未执行，不推断结果。
- `PENDING`：已提交但等待审核、部署、设备或平台回执。

维护本技能时，使用仓库中的 `evals/evals.json` 做边界回归；预期结果不是执行结果，只有实际运行后才能报告行为验证通过。
